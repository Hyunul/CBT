# 성능 측정과 개선

로컬 Docker Compose 스택에 k6로 부하를 걸어 병목을 찾고 고친 기록입니다. 운영 서버에서 잰 값이 아니며, 수치는 아래 환경에서만 의미가 있습니다.

## 환경과 방법

- **환경**: Windows 10 + Docker Desktop(WSL2, 12 vCPU, 16GB). 백엔드·MySQL 8·Redis 7이 한 머신의 컨테이너로 실행됩니다. 백엔드 JVM 힙 최대 768MB, Hikari 풀 기본값 10.
- **경로**: nginx는 응시 시작을 IP당 초당 1회로 제한하므로, 애플리케이션 자체를 재려고 백엔드에 직접 요청합니다(`docker-compose.override.yml`로 `127.0.0.1:18081`만 노출).
- **시나리오**
  - [`loadtest/attempt-flow.js`](../loadtest/attempt-flow.js): 필기 100문항 응시 한 번 — 시작 → 문항 조회 → 자동 저장 5회 → 제출 → 결과 조회. 자동 저장은 앱과 같이 매번 전체 문항을 보내고 안 푼 문항은 `null`입니다.
  - [`loadtest/start-only.js`](../loadtest/start-only.js): 응시 시작만 초당 50회 고정 속도로 30초.
- **원칙**: 한 번에 한 가지만 바꾸고, 재빌드 직후의 JIT 미예열 구간을 피하려고 워밍업 후 잽니다.

```sh
k6 run -e BASE_URL=http://127.0.0.1:18081 -e EXAM_IDS=17,18,19,20,21,22,23,24 -e VUS=200 loadtest/attempt-flow.js
k6 run -e BASE_URL=http://127.0.0.1:18081 -e EXAM_ID=24 -e RATE=50 loadtest/start-only.js
```

## 1. 처리량 한계 찾기

| 동시 사용자 | 처리량 | p95 | 오류 |
| --- | --- | --- | --- |
| 50 | 404 req/s | 176ms | 0% |
| 200 | 414 req/s | 556ms | 0% |

사용자를 4배로 늘려도 처리량은 그대로이고 지연만 늘었습니다. 약 410 req/s(응시 약 45회/초)에서 포화됩니다.

- **커넥션 풀이 원인인가**: 풀을 10 → 30으로 늘려도 처리량은 같고 p95만 나빠졌습니다(앞선 버전의 시나리오로 측정). MySQL로 동시 작업만 더 몰렸을 뿐이라 풀은 병목이 아닙니다.
- **MySQL이 어디에 시간을 쓰나**: `performance_schema.events_statements_summary_by_digest`로 문장별 누적 시간을 봤습니다.

| 순위 | 문장 | 평균 |
| --- | --- | --- |
| 1 | `COMMIT` | 7.3ms |
| 2 | 답안 `INSERT`(한 행씩) | 0.17ms |
| 3 | 채점 답안 `UPDATE`(한 행씩) | 0.16ms |
| 4 | 문항 목록 `SELECT` | 0.9ms |
| 5 | 시험 조회 + `COUNT(attempts)` 서브쿼리 | **7.1ms** |

`COMMIT`은 Docker Desktop 디스크의 동기화 비용이라 코드 문제가 아니고, 답안 유실을 막는 `innodb_flush_log_at_trx_commit=1`을 낮추는 것은 내구성을 포기하는 일이라 건드리지 않았습니다. 5위가 데이터가 쌓일수록 커지는 진짜 문제였습니다.

## 2. 응시가 쌓일수록 응시 시작이 느려지던 문제

**원인**
- `Exam.attemptCount`가 `@Formula("(select count(a.id) from attempts a where a.exam_id = id)")`라서 시험을 읽을 때마다 그 시험의 응시 전체를 셌습니다.
- 응시 시작은 문항 교체와 조정하려고 시험을 `SELECT … FOR UPDATE`로 잠가 읽습니다. 잠금을 쥔 채 응시 전체를 세므로 같은 시험의 응시 시작이 줄줄이 대기했습니다.
- 정작 이 값은 메인 목록의 인기 시험 정렬에만 쓰였고 화면에는 표시되지 않았습니다.

**수정**: `@Formula`를 없애고, 인기 시험 목록을 만들 때만 시험 id별로 한 번 집계합니다(`ExamRepository.findPopularIds`).

**결과**: 같은 시험에 응시 기록 20만 건을 넣고 응시 시작을 초당 50회로 30초 호출했습니다.

| | 응시 2,639건 | 20만 건 · 수정 전 | 20만 건 · 수정 후 |
| --- | --- | --- | --- |
| p95 | 9.4ms | **7.04s** | **10.1ms** |
| 처리한 요청 | 1,501 / 1,500 | 1,049 (목표 속도 미달) | 1,500 / 1,500 |

데이터가 80배 늘어도 응시 시작 지연이 그대로입니다. 대신 메인 목록이 조회 때마다 응시를 집계해 20만 건 기준 50~100ms가 걸립니다. 잠금 없이 한 번만 돌지만, 응시가 수십만 건을 넘으면 시험별 카운터 컬럼이나 캐시로 바꿔야 합니다.

## 3. 채점·자동 저장 UPDATE 배치

**수정**: `hibernate.jdbc.batch_size=50`, `order_updates`, MySQL URL에 `rewriteBatchedStatements=true`(이 옵션이 없으면 드라이버가 배치를 한 문장씩 보냅니다).

**DB 왕복 수**(Hibernate 세션 통계로 확인)

| 요청 | 이전 | 이후 |
| --- | --- | --- |
| 제출(채점 100개 + 응시 1개 UPDATE) | 101회 | **3회** |
| 자동 저장 2~5회차(UPDATE 20개) | 20회 | **1회** |
| 자동 저장 1회차(답안 100개 INSERT) | 100회 | 100회 — IDENTITY 키는 Hibernate가 배치하지 않음 |

**지연과 처리량**: 50명에서 제출 p95가 205ms → 163ms·181ms(2회 측정)로 낮아졌지만, 처리량은 같은 조건에서 459·408 req/s로 측정마다 크게 흔들려 개선을 주장할 수 없습니다. 이 환경의 병목은 왕복 수가 아니라 요청마다 한 번씩 하는 `COMMIT`의 디스크 동기화이기 때문입니다. DB까지 네트워크 지연이 있는 환경일수록 효과가 커지는 설정이라 유지했습니다.
